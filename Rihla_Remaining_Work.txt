# 0. Purpose and Non-Negotiable Architecture

Rihla uses the following ownership model:

- **`DT_ItemData` / `S_ItemInfo`** define what an item type is.
- **`S_ItemSlot`** stores state belonging to a specific inventory instance/stack.
- **`BPC_Inventory`** owns inventory state and all inventory mutations.
- **`PlayerStatsComponent`** owns player resources.
- **`BPC_QuickSelect` / `WBP_QuickSelectMenu`** own quick-select presentation and selection flow, not inventory state.
- **`BuildComponent`** owns live building state.
- **`S_GameData`** owns persistent save state.

The following rules are mandatory:

1. **Static item data is never modified at runtime to represent a particular item instance.**
2. **Array indices are positional only, never identity.**
3. **Every unique inventory instance/stack carries a stable `ItemInstanceID` (`FGuid`).**
4. **Inventory mutations are authoritative and transactional.**
5. **UI requests gameplay operations; UI does not directly mutate inventory or player stats.**
6. **Effective item values are resolved through one shared path instead of being recalculated independently in multiple systems.**
7. **Transient state and persistent state are explicitly separated.**
8. **A feature must not introduce a second source of truth for data another existing system already owns.**

# 2. Core Architecture Rules

## 2.1 Static item data

`DT_ItemData` and its associated item-information structures define what an item **type** is.

Examples:

- Item name.
- Description.
- Category.
- Base damage.
- Base armor.
- Base restoration values.
- Mesh/class references.
- Material fusion properties.

Static item data must never be modified at runtime to represent one particular item instance.

---

## 2.2 Per-instance inventory state

`S_ItemSlot` stores state that belongs to the actual inventory instance/stack.

Examples:

- `ItemInstanceID`.
- `ItemID`.
- Quantity.
- `CurrentDurability`.
- `FusedMaterialID`.
- `TimesUsed`.
- Cooked effect overrides.
- Other future per-instance state.

Dynamic values must remain on the slot, not in the shared DataTable row.

---

## 2.3 Item type vs item instance

These meanings must never be mixed.

### `ItemID`

Identifies the **item type/static definition**.

Example:

```text
ItemID = Rock
```

All Rocks use the same static Rock row.

### `ItemInstanceID`

Identifies the **specific inventory instance/stack**.

Example:

```text
ItemInstanceID = 8F...
ItemID = Rock
Quantity = 1
```

Another Rock can have the same `ItemID` but a different `ItemInstanceID`.

---

## 2.4 Stable item identity

Array indices are positional only.

An index can change when:

- Items are removed.
- Items are sorted.
- Stacks are split.
- Stacks are merged.
- Other inventory mutations occur.

Every operation that means:

> "this exact item"

must use `ItemInstanceID`.

This includes:

- Equip.
- Unequip.
- Drop.
- Consume/use.
- Fuse.
- Unfuse.
- Durability changes.
- Build-source tracking.
- Usage tracking.
- Hover/selection state.
- Pending replacement transactions.

Indices may still be used internally and transiently inside a function after resolving an instance ID to its current slot.

---

## 2.5 Item-instance lifecycle rules

### Creation

When an item instance/stack is first created:

- Generate one new valid `FGuid`.
- Store it in the slot.
- Never regenerate it simply because the slot moved.

### Split

When a stack is split:

- The original stack keeps its original `ItemInstanceID`.
- The new stack receives a new `ItemInstanceID`.
- The original stack retains its existing `TimesUsed` unless the gameplay action explicitly says otherwise.
- The new stack starts with the appropriate new-instance state.

### Merge

When two compatible stacks merge:

- One instance must be chosen as the surviving instance.
- The surviving instance keeps its `ItemInstanceID`.
- The absorbed instance is removed completely.
- Do not generate a new ID for the merged stack unless the project explicitly decides that a merge represents a new instance.
- `TimesUsed` follows the surviving instance.

The merge/split rules must be deterministic.

---

## 2.6 Equipment identity

`EquippedItemIDs` must store `ItemInstanceID` values, not only `ItemID` names.

This is required once two identical item types can coexist.

Example:

```text
Sword A
ItemID = Sword
InstanceID = A

Sword B
ItemID = Sword
InstanceID = B
```

Equipment must be able to say:

```text
Equipped Instance = B
```

rather than merely:

```text
Equipped ItemID = Sword
```

Do not implement later systems assuming an ItemID-only equipment map is sufficient.

---

## 2.7 Inventory authority

`BPC_Inventory` remains the authoritative owner of:

- `ItemSlots`.
- Adding/removing items.
- Stack operations.
- Equipment.
- Capacity.
- Item-instance state.
- Effective item-stat/effect queries.
- Usage tracking.
- Sorting/view generation.
- Inventory-side transaction validation.
- Save/load inventory state.

Other systems request inventory operations through functions on `BPC_Inventory`.

They do not directly edit `ItemSlots`.

---

## 2.8 Player-resource authority

`PlayerStatsComponent` owns:

- Health.
- Temporary health.
- Stamina.
- Temporary stamina.
- Battery.

Other systems call the component.

They do not directly write those values.

The component should not become responsible for movement, combat, UI, or inventory rules.

---

## 2.9 Build authority

`BuildComponent` owns live building state:

- Current held actor.
- Whether it came from inventory.
- Source `ItemInstanceID`.
- Physics handle.
- Snap preview.
- Rotation.
- Hold distance.
- Gizmo.
- Placement/cancel state.
- Detach state.
- Temporary build actors.

`BPC_Inventory` owns the inventory transaction associated with an inventory-originated build.

`BuildComponent` must never directly mutate `ItemSlots`.

---

## 2.10 Save authority

`S_GameData` is the authoritative persistent snapshot.

Every feature that introduces persistent state must specify how that state enters/leaves `S_GameData`.

Transient runtime state must not automatically become save data.

---

## 2.11 Effective-value authority

Where a value can differ between the static row and the actual inventory instance, create one centralized effective-value query.

The project should eventually have a consistent family of functions such as:

- `GetEffectiveDamage(ItemInstanceID)`.
- `GetEffectiveDefense(ItemInstanceID)`.
- `GetEffectiveItemEffects(ItemInstanceID)`.

The exact implementation can be Blueprint or C++, but there must not be several independent copies of the same calculation.

# 3. Foundational Prerequisites

These are architectural contracts rather than new gameplay features. Establish them before implementing the later systems that depend on them.

## 3.1 Verify/complete `ItemInstanceID` migration

Before implementing fusion, building inventory integration, durability, usage tracking, or sorting:

1. Add `ItemInstanceID : FGuid` to `S_ItemSlot` if it is not already present.
2. Generate it exactly once when creating a new instance/stack.
3. Add `FindSlotByInstanceID` to `BPC_Inventory`.
4. Ensure newly loaded legacy slots receive an ID if none exists.
5. Change equipment references to instance IDs.
6. Ensure UI-created/selected slots carry both `ItemID` and `ItemInstanceID`.
7. Audit existing functions for index-based identity assumptions.
8. Do not begin Part O until this audit is complete.

---

## 3.2 Establish effective item-effect resolution

Before Part E and Part K become large, define one resolution path:

```text
ItemInstanceID
    ↓
Find S_ItemSlot
    ↓
Read ItemID
    ↓
Get S_ItemInfo from DT_ItemData
    ↓
Apply active per-instance overrides
    ↓
Return effective item effects
```

At minimum, the effect model must support:

- Health restore.
- Stamina restore.
- Temporary health.
- Temporary stamina.
- Future status/buff effects.

The project may begin with scalar fields, but callers must not each implement their own effect resolution.

---

## 3.3 Runtime transaction rule

Inventory-changing operations must have a clear commit point.

Examples:

```text
Use:
validate → resolve effects → apply → consume → register use → commit

Swap:
validate → reserve → add new → commit old removal → drop old

Cook:
validate → resolve recipe → validate output → prepare output → commit
        output + ingredient consumption atomically

Build:
spawn preview → hold → confirm successful placement → consume source instance
```

Other systems must not observe a half-completed inventory transaction.

# Part A — Player Stats Foundation

**Status:** Native C++ implementation already exists. The remaining work is Character integration, gameplay/UI access, and save integration.

## Goal

Make `PlayerStatsComponent` the one authoritative source for player health, stamina, temporary resources, and battery.

## A1. Add the existing component

Do not create another stats component.

Add the existing:

`PlayerStatsComponent`

to the player Character.

---

## A2. Units

These units are fixed:

### Health

- `1 Health unit = 1 quarter-heart`.
- `4 Health units = 1 full heart`.
- Example: `MaxHealth = 12` means 3 hearts.

### Stamina

- `1.0 Stamina unit = 1 full stamina-wheel segment`.
- Example: `MaxStamina = 3.0` means three full stamina segments.

### Battery

- `1.0 Battery unit = 1 full battery segment`.
- `MaxBattery` and `CurrentBattery` start at `0`.
- Battery capacity is granted by progression.

Increasing `MaxBattery` does not automatically refill `CurrentBattery` unless a specific progression rule says so.

---

## A3. Existing API

The delivered C++ already provides:

- `RestoreHealth`.
- `RestoreStamina`.
- `AddTemporaryHealth`.
- `AddTemporaryStamina`.
- `TakeDamage`.
- `DrainStamina`.
- `RestoreBattery`.
- `DrainBattery`.
- Temporary-resource clear functions.
- Save application.
- Max-resource setters.

Do not create duplicate Blueprint-only versions.

---

## A4. Damage

`TakeDamage`:

1. Consumes temporary health first.
2. Applies remaining damage to normal health.
3. Clamps to zero.
4. Broadcasts changes.
5. Marks the player dead when both health pools are depleted.

Death animations, movement restrictions, camera behavior, respawn, and overall gameplay mode remain Character/gameplay responsibilities.

---

## A5. Temporary-resource policy

The component owns the resource values and mutation API.

Gameplay systems must define:

- Stack vs replace.
- Expiration.
- Removal.
- Death behavior.
- Restoration behavior.

Do not let each food/effect system invent different rules.

---

## A6. Access

Use a clean path:

```text
Widget / Gameplay system
        ↓
Character
        ↓
PlayerStatsComponent
```

Avoid repeated global world searches.

---

## A7. Progression

Use:

- `SetMaxHealth`.
- `SetMaxStamina`.
- `SetMaxBattery`.

Do not let arbitrary systems directly assign max values.

# Part G — Capacity Enforcement

## Goal

Enforce weapon/bow/shield capacity through one authoritative inventory-add path.

## G1. Central gate

All inventory entry points must use the same add logic:

- Ground.
- Containers.
- Cooking.
- Rewards.
- Future systems.

## G2. Capacity semantics

Weapon/bow/shield capacity is occupied **inventory-instance/slot capacity**, not raw quantity.

Stackable item quantity/stack size is a separate concept.

## G3. Check order

Before mutation:

1. Resolve item type/category.
2. Check whether the category is capacity limited.
3. Attempt valid stack merging if applicable.
4. If no merge is possible, count occupied instances.
5. Compare against capacity.
6. Return a structured result.

Possible results:

- Success.
- Invalid item.
- Invalid data/class.
- Category full.
- Other failure.

## G4. Capacity ownership

UI never independently decides whether the category is full.

## G5. Upgrades

Create:

`UpgradeCategoryCapacity(Category)`

It:

- Increases current capacity.
- Clamps to maximum.
- Rejects upgrades at maximum.

Future NPC/currency systems call this function.

# Part H — Full Inventory Swap

## Goal

Safely replace one item when a limited category is full.

## H1. Popup

Display:

> Inventory full — drop [existing item] to make room?

Show:

- Existing item.
- Incoming item.
- Confirm.
- Cancel.

## H2. Player selection

Initially the player explicitly chooses the item to replace.

## H3. Atomic replacement

Treat replacement as one transaction:

```text
Validate incoming item
→ Validate old ItemInstanceID
→ Reserve old slot internally
→ Prepare/validate incoming instance
→ Commit incoming insertion
→ Commit old removal
→ Spawn/drop old item
```

The old item must not be permanently dropped before the new one has successfully entered inventory.

Other systems must not see an inconsistent half-swapped inventory.

## H4. Complete item state

The transaction preserves the complete incoming instance state:

- ItemID.
- Quantity.
- Durability.
- Fusion state.
- Cooked overrides.
- ItemInstanceID.
- Other per-instance state.

## H5. Failure

If the transaction cannot commit, restore the exact previous inventory state.

## H6. Cancel

Cancel changes nothing.

## K2. Temporary ingredient selection

Selected ingredients remain in temporary cooking state until the cook transaction commits.

## K3. Recipe lookup

Create:

`DT_Recipes`

with deterministic ingredient keys.

Ingredient order must be canonicalized.

Counts must matter:

```text
A + B
≠
A + A + B
```

## K4. Hybrid recipe resolution

Use:

```text
Exact recipe
→ if no match
→ deterministic generic effect rules
```

Do not make one DataTable row for every possible combination.

## K5. Per-instance food effects

Do not modify `DT_ItemData` with generated cooking results.

At minimum, `S_ItemSlot` supports:

- `OverrideHealthRestore`.
- `OverrideStaminaRestore`.
- `OverrideTemporaryHearts`.
- `OverrideTemporaryStamina`.

Use:

```text
-1 = use static ItemInfo value
>= 0 = use instance override
```

As effect types grow, consolidate these into a reusable item-effect structure rather than adding unlimited one-off override fields.

## K6. Generic meal rows

Use generic rows such as:

- Basic cooked dish.
- Hearty dish.
- Energizing dish.
- Enduring dish.
- Other intended categories.

## K7. Atomic cooking transaction

The complete operation is:

```text
Validate ingredient instances
→ resolve recipe
→ calculate output effects
→ validate output capacity/stacking
→ prepare meal instance
→ commit meal + ingredient consumption atomically
```

The player must never receive both ingredients and the meal after a supposed successful cook, nor lose ingredients without receiving the output.

## K8. Eating

`UseItem(ItemInstanceID)` resolves cooked overrides through the shared effective-effect path.

## K9. Buff effects

Mighty/Tough and similar effects require a future status/buff system.

Do not fake these by abusing health/stamina fields.

## L1. Save version

- ItemID.
- Quantity.
- CurrentDurability.
- FusedMaterialID.
- TimesUsed.

Save/load `EquippedItemIDs` as instance IDs.

## L4. Capacity/progression

- Current health.
- Max health.

- Current stamina.
- Max stamina.
- Current battery.
- Max battery.

One authoritative system constructs `S_GameData`.

# Part N — Durability and Weapon Breaking

## Status

Blocked until actual combat events exist.

## N1. Primary API

`DamageItem(ItemInstanceID, Amount)`

This is the authoritative durability mutation.

Optional wrapper:

`DamageEquippedItem(EquipmentCategory, Amount)`

resolves the equipped instance and calls `DamageItem`.

## N2. Durability

`DamageItem`:

1. Resolves the instance.
2. Validates it.
3. Subtracts durability.
4. Clamps to zero.
5. Detects break.
6. Refreshes/broadcasts state.

Combat never directly edits `CurrentDurability`.

On break:

1. Resolve exact instance.
2. Unequip it if equipped.
3. Remove it.
4. Clear equipment reference.
5. Invalidate stale quick-select/selection references.
6. Trigger VFX/SFX.
7. Refresh UI.

## N4. Combat integration

Melee calls `DamageItem` on the actual durability-consuming event.

Bow combat defines its own bow/arrow durability and consumption rules.

- Store cooked generated values in `DT_ItemData`.
- Modify base weapon damage when fusing.
- Use `ItemID` as the identity of a specific inventory instance.

- Let Quick Select maintain a second inventory database.
- Let BuildComponent directly remove inventory items.
- Let Character duplicate BuildComponent's build-action bindings.
- Let combat directly edit durability.
- Let multiple systems increment `TimesUsed`.
- Let each UI implement independent sorting.

- Infer aiming/throwing from UI state.

- Create a separate DataTable row for every possible cooking combination.

- Let individual food callers invent different temporary-resource rules.
- Delete `WBP_ContainerUI` before checking all references.

# 9. Final Implementation Principle

Rihla should grow by adding systems around the existing architecture, not by bypassing it.

The intended data flow is:

```text
DT_ItemData / S_ItemInfo
        ↓
defines item type
        ↓
S_ItemSlot
        ↓
stores specific instance state
        ↓
BPC_Inventory
        ↓
owns and mutates instance
        ↓
Effective Item Queries
        ↓
UI / Quick Select / Food / Fusion / Combat
```

Player resources:

```text
PlayerStatsComponent
        ↓
Health / Stamina / Battery
```

Building:

```text
BPC_Inventory
        ↓
resolves ItemInstanceID → ItemID → BuildableActor class
        ↓
BuildComponent
        ↓
owns live build state
        ↓
successful placement
        ↓
BPC_Inventory consumes exact source instance
```

Persistence:

```text
Runtime authoritative systems
        ↓
S_GameData
        ↓
SaveVersion + persistent state
```

Presentation:

```text
Authoritative runtime state
        ↓
Inventory / Quick Select / Wardrobe UI
```

The key rules remain:

> **ItemID answers "what is it?"**  
> **ItemInstanceID answers "which exact one is it?"**  
> **BPC_Inventory answers "what is in the inventory?"**  
> **PlayerStatsComponent answers "what resources does the player have?"**  
> **BuildComponent answers "what is currently being built?"**  
> **S_GameData answers "what persistent state should survive a reload?"**

When a new feature appears to require duplicating existing state, first determine which existing system already owns that state and expose a clean API instead.
